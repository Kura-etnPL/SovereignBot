# V4.3 P39 Conversation pagination acceptance

Date: 2026-09-03
Scope: Canonical Product Plan §35 long Conversation history

P39 keeps `ConversationStore.get(id)` as the complete main-process read for dispatchers and internal callers, and adds the same-store bounded `getPage()` path for renderer reads. The typed `conversation:get` contract now accepts only `conversationId`, `limit` (1–100), and an existing conversation-local `beforeMessageId`; omitted limits normalize to 100. The response preserves the existing summary and message fields and adds `pageInfo.total`, `pageInfo.hasOlder`, and an opaque next cursor. Unknown, stale, and foreign cursors fail closed.

The ordinary Conversation UI initially renders the latest 100 messages, loads older pages through an explicit `Load older messages / 加载更早消息` action, prepends them in order without duplicates, and restores the scroll anchor after layout. Polling merges newer messages into the current bounded window, conversation switches reset pagination state, and rendered message DOM is capped at 300 rows. Existing send, reply, mention, delivery, voice, mark-read, Team activity, and navigation paths remain on the existing typed APIs.

- limit, unknown-field, and foreign-cursor requests are rejected at the typed IPC boundary;
- restart rebuilds the same latest page from the durable conversations JSON.
